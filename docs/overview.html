Scoring every conversation, not a sample of them

Contact-centre quality review reads 1–3% of interactions by hand and extrapolates from it. This tool scores all of them against rubrics you write, by replacing the language model in the loop with a classifier that costs about five thousandths of a cent per conversation.

How it works

Two mechanisms carry the whole design.

One request per transcript, however many rubrics

Jev is a classifier, not a language model. It reads the transcript once and answers every attached question against it in parallel, so a library of thirty rubrics costs the same single call as one. A conventional LLM judge re-reads the transcript per dimension and bills output tokens for prose nobody reads.

Answers come back typed — a probability for a true/false question, a level for a score, an option key for a choice — so nothing is parsed out of prose and nothing can arrive in a shape the code did not expect.

Raw answers are stored; policy is applied on read

The model is never asked for an overall grade. It reports each rubric separately, and the weighted composite is computed when you look at the results. That is what makes the weight sliders instant: moving one re-ranks an entire history with no request, no cost, and no risk of old scores being incomparable with new ones.

Confidence routes, it does not grade

Score and option answers carry a confidence; true/false answers do not, because there the probability already carries it. A low confidence usually means the transcript did not contain enough to judge — so those sessions are flagged for a person rather than scored down. Human attention lands where the machine was genuinely unsure instead of on a random sample.

Long transcripts split, and fold back by meaning

A transcript over the context budget is cut on turn boundaries and each part scored separately. How the parts recombine is derived from the rubric, not asked of the author: a violation counts if it happened anywhere, an outcome is settled by the end of the conversation, and a graded quality is averaged across it. Averaging everything would quietly destroy the first case — one breach among clean chunks disappears.

Driving it with a coding agent

Setup is two commands. After that you describe what you want measured.

#  once
npm link
ln -s $PWD/skills/jev-cognigy-qa ~/.claude/skills/jev-cognigy-qa

The second line installs an agent skill. It teaches Claude Code, Codex or anything else that reads skills which rubric type to reach for, how to read a confidence number, and when to hand a question back to you rather than guess.

Point your agent at the repository:

Clone https://github.com/pb-crackers/Jev-Cognigy-QA-Suite, follow its
AGENTS.md to set it up, then help me QA my Cognigy conversations.

One line, pasted into Claude Code, Codex, or anything else that reads a repository. It installs the tool and the skill, then hands the credentials step back to you — an agent should never be handling your API keys.

After that you talk to it normally:

“Check whether our agents are confirming details back to customers before acting. Score last week.”

  1. It writes the rubric

    Turning the request into a question, an answer type and the boundary conditions. You never touch JSON.

    $ jev-cognigy-qa rubric add --json '{…}'

  saved Confirmed details back
  type boolean   combine last (derived)

  2. It runs the date range

    Results go to stdout as JSON, progress to stderr, so the output pipes cleanly into whatever comes next.

    $ jev-cognigy-qa score --project V2V --from 2026-09-15 --to 2026-09-19

  12 sessions   $0.000599   4.0s   9 flagged

  3. It reads the findings back to you

    Not a dump of numbers. A synthesis, ranked worst first, with the transcript excerpts that justify each one — written to be handed onward to an agent working on the Flow itself.

    $ jev-cognigy-qa brief | pbcopy

What makes it drivable

The design decisions that matter for an agent are small and dull, and all of them were things that broke the first time:

  • JSON on stdout, progress on stderr. Output stays pipeable while a long run still reports what it is doing.
  • No flags to remember. The command loads its own configuration; an agent that forgets a flag gets a confusing error and gives up.
  • Configuration resolves from the install, not the working directory. Otherwise the same command works in one folder and reports itself unconfigured in the next.
  • Validation returns every problem at once, so a rejected rubric tells the agent everything to fix rather than one thing per attempt.
  • Credentials stay with you. The skill tells the agent to hand init back to the user rather than handle API keys.
